# 通用排障流程改进：对照预注册

## 基线与目的

基线固定为 `1ca4cbdb2c34a0646ec3271d2ef14172a4465044`（2026-10-30 当前版本检查点）。
本轮比较新的通用发布安全、完整流时限/故障分类与可选本案证据检查，不调整业务规则，不切换主模型或恢复语义复核。
候选版本以开跑前提交及源码/内核构建哈希为准；未冻结前不启动真实模型对照。

## 用例

共8例：T001、T003、T004、T006、a12c3554、c4a2f188、ec4dd656（2898ed55为别名）、81ca3256。
题面均仅取原首条真实user.content，不传历史assistant/tool/评分信息，9张原图字节保留，全部输入哈希已写本地清单。
这些例子均已用于排查或调优，**不是独立留出集**。
旧参考中没有独立证据支持的归因不能当金标准，评分区分事实/机制/本案因果/未知。

## 控制条件

- 同源 `deepseek-v4.1-flash`、本机同一上游、同一凭据、推理 `max`、输出上限128000、上下文1048576。
- 两臂均 `REVIEW_MODE=off`、`ANSWER_GUIDE=off`、`ANSWER_ID_CHECK=off`，首轮15分钟及现有收尾预算不变。
- 两臂模型调用配置上限240000毫秒、应用总attempt配置1；基线SDK额外retry=1、候选SDK=0是被测重试修复差异，逐次记实际请求，不虚称两者内部实现相同。
- 候选 `CASE_EVIDENCE=1`，只读本会话结果的可选检查工具，普通模型请求未强制二次语义复核；不把工具verified当因果已证实。
- 每次只跑同一题的基线/候选两臂，全球上游并发2、每run并发1；多图转写也过统一排队。记录queueMs与端到端时间。
- 18个源码仓库复制成固定提交的detached镜像，两臂同路径，镜像不自动同步；prod-config保留源仓库已有Windows非法文件名稀疏排除。图谱同一镜像重建、两臂同文件哈希。
- 员工会话库、运行身份、日志独立，不接飞书通道，不改8600线上服务。每个run真实入口都是各自版本的AgentService/AgentCore，不拿手工草稿冒充真实输出。
- 业务MySQL/Loki仍是实时只读源，未做整库快照。相同题近同时查询并保留响应及时间；遇到值漂移标记不适合归因，而不是声称所有业务证据恒定。
- 全部未作答、异常、冻结、重试、人工干预保留；不得挑分数最高的一次。基础设施未启动不是模型低分，不与有效已答结果混算。

## 测量

1. 交付：完整/部分/未交付、原因分类、草稿被格式/隐私/证据检查挡住的数量、错误确定性结论。
2. 业务：原问题是否真正答上，对象关系/时点/成因是否由证据支持；事实要点按hit/partial/miss计分，不把机制存在等同当次成因。
3. 可用性：只看最终结论是否清楚、能否直接回复、是否把工具本能核实的事推回客服；不强制没有证据时也必须下结论。
4. 用时与成本：发出问题至done、实际模型请求/排队/重试时间、token、工具调用数。故障样本的终止耗时单列。

## 决策规则

- 所有离线安全不变量必须通过；泄露、全失败错发确定结论、取消后仍持续消耗等为阻断问题。
- 端到端至少7例有成对有效运行；第一轮8例×2臂全部列出。若小样本边缘差异，不据此宣布优越或自动上线，先做预先确定的第二轮重复。
- 用同一评分标准对来源隐藏的全部新旧答案统一评分；同时看正确性、清晰度和失败率，不只看号码出现率/要点字面命中。
- 若准确性或可用性明显倒退，不启用候选证据工具；工程安全修复可单独作为更小候选继续对照。
- 此文是预注册计划而非测试结果；最终报告补上实际版本、有效样本、失败原因与是否发布。
