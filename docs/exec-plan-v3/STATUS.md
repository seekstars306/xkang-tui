### 四、服务归属映射（`lookup_service`）

**动因**：T007 中模型查 `cxy-hotel` 13 次、`cxy-booking` 0 次，而可订校验日志在 `cxy-booking`。

扫出三个反直觉的结构问题：

| 问题 | 实例 |
|---|---|
| 目录名 ≠ 部署名 | `cxy-booking` 的配置在 `prod-config/cxy-dpxt` |
| 一个仓库多个服务 | `skt_dpxt_background` 承载 4 个服务 |
| 一个包根多个服务 | `com.llb.cxy` 被 3 个服务共用 |

产出 `service_map.json`：12 个服务，8 个 `high`（jar 或 app 名直接证据）、2 个 `low`、2 个 `none`。

**实测效果**：`cxy-booking` 查询 0→6 次，`cxy-hotel` 13→1 次；结论从「成因尚未定位」推进到「连续 7 晚房态核验未通过」。

**三个必须先清除的障碍**：①runner 白名单过滤（工具存在但客户端不可见）；②prompt 未提及；③隔离服务端 cwd 不是项目根导致映射加载失败。

### 五、方法论收获

1. **「读到了」≠「写出来了」**（T006）：工具层已获取正确证据，答案却停在现象层。这类错误复核抓不到，因为答案自身不矛盾。
2. **数据可能被人工修改**（T006）：用户报障后手动改过 `fpstatus`，该表无 `update_time`，修改在库里隐形。判断「状态是否变化」前必须排除人工干预。
3. **多份答案不等于多份真相**（T007）：三份外部答案中，一份机制最精确但推断不适用，一份**编造了 4 个时间戳和 2 个 ID**，结论方向却碰巧对。
4. **合成样本不可信**：我自造的分类测试集 10/10，真实工单才暴露问题。
