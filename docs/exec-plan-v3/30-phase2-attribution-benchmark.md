# Phase 2 · 失败归因与复核基准

前置：Phase 1 的 S5 必须已经完成（要用它的台账和区间函数）。本阶段**要花模型费用**，每一项开始前先向用户报预算并取得同意（关口 G3）。

本阶段回答两个问题：**(1) 现在的错误里有多少是"老问题"造成的？ (2) 复核到底该用哪个思考档位？** 这两件事都必须**在任何复核提示词改写之前**完成，否则后面的改动效果无法归因。

---

## M1 失败归因：把每一次失败归到一类

**目标**：把已有全部失败逐条归入固定类别，产出分布，并回答"老问题占多少"。**这是本阶段最省钱、信息量最大的一件事**，因为没有新的模型调用——材料早就跑完了。

**依据**
- 已有的 120 次受控运行（20 题 × 3 轮 × 2 版本）在 `tests/eval/reports/server-harness-20261009/acceptance-verified/`，含 `manifest.json`、`grades.json`、逐次运行目录。摘要：新版本 22/60 完整可用、60/60 正常结束、3 次严重误导；旧版本 13/60、12 次严重误导。
- 同证据对照在 `tests/eval/reports/model-ceiling-20261009/`（`scores/`、`evidence/`、`workflow/`、`core-180-workflow/`）。
- 已知可疑的"老问题"清单在 `00-README.md` §3。

**类别（每行只能选一个，外加一个兜底类）**
| 编号 | 类别 | 判据 |
|---|---|---|
| 1 | 代码版本或镜像污染 | 模型读到的工具结果里出现未提交改动、旧版路径、重复仓库、过时文档/注释、`.bak` 配置，且它影响了结论 |
| 2 | 历史数据由旧逻辑产生 | 数据与现行代码自洽但模型按新代码解释（或反之），决定性证据是"数据产生时间对应的实现" |
| 3 | 取证不足或证据包有缺口 | 决定性证据根本不在场；工具调用失败、超时、结果被截断 |
| 4 | 推理问题 | 适用范围说大、概念混淆（票务状态与资金状态、应收与实收、月结与现结、受理与到账、生成通知与实际送达、预订失败与出单失败、保留配置与当前有效） |
| 5 | 输出层问题 | 结论对，但附带断言或客服话术里多出承诺/时效/动作 |
| 6 | 复核或流程问题 | 超时、格式失败、`performed_action` 误拦、材料超预算 |
| 7 | 参考答案或评分本身有错 | 评分细则与参考答案对不上，或评分者判错 |
| U | 无法判定 | 证据不足以下判断——**允许存在，不要硬塞进上面任何一类** |

**改动点**
- 新增 `tests/eval/reports/exec-v3/attribution.tsv`（被 git 忽略），列：
  `run_id, variant, caseId, round, grade, severeMisleading, category, decisive_evidence_present, saw_stale_artifact, evidence_pointer, notes`。
- 新增 `scripts/eval/build_attribution_sheet.ts`：把 `grades.json` 与逐次运行目录拼成上表的**空白骨架**（程序能填的列：run_id、variant、caseId、round、grade、severeMisleading；其余等人填）。
- 新增 `scripts/eval/scan_run_evidence.ts`：对每次运行的工具结果做**确定性扫描**（不调模型），输出布尔列：
  - 结果里是否出现 `prod-config`、`*.bak`、`*.old`、`node_modules`；
  - 是否出现同名但不同仓库的文件（`skt_cxy` vs `skt_dpxt_background` 的 296 个同名文件，先建索引再比对）；
  - 是否出现 `orderNew`/`invoiceNew`/`hotelNew`/`entityOld` 这类新旧并存路径；
  - 是否出现被标注为历史的问题记录文档；
  - 是否出现过"镜像有未提交改动"的迹象。
  这一列是**事实**，不是判断，所以它可以是金标准。

**步骤**
1. 跑 `scan_run_evidence.ts`，产出事实列。
2. 逐条填 `category`：**必须给出 `evidence_pointer`**（哪个文件、哪一行工具结果、哪句话）。不能给出指针的行只能填 `U`。
3. 汇总分布：总数、每类条数、占比；第 1、2 类的条数与涉及题目。
4. 对第 1、2 类的失败，在 S2/S3 完成后重跑同题同轮次，记录能消掉多少。
5. 打印一份"抽查包"：随机 20 条（优先含严重误导和 `U`），附上指针，交开发确认（**G2**）。

**验收**：`attribution.tsv` 每一行都有 `category` 与 `evidence_pointer`（`U` 除外）；分布表存在；抽查包的 20 条由开发确认或改判并留痕；结论写成"X 条失败中第 1 类 a 条、第 2 类 b 条……"，**不得**写成"准确率提升"。

**依赖**：无（可立即开始，不必等 Phase 1）。

**关口**：G2（开发抽查 ≥20 条）。

**风险与回滚**：归因是模型做的，**是银标签**。`evidence_pointer` 就是为了让人能复查。`U` 类占比过高（比如超过三成）说明材料不足，要停下去补材料，而不是扩大类别定义。

## M2 复核基准：已知错误答案 + 已核对正确答案

**目标**：给复核建一份可重复的标尺。改动复核时用它回答"检出率降没降、误拦多不多"。

**依据**
- `scripts/eval/review_optimization.ts` 已经有一套**受控虚构用例**（18 条），做法是：`expected` 判断在代码里预登记、**从不发给复核模型**；每次运行写 `manifest.json`、拒绝覆盖既有目录、把源码副本存进 `out/source/`。**照这个模式做，不要另发明一套。**
- 可补充的真实材料：120 次验收里的 38 次失败、同证据测试里的误导答案、以及历史上被人工判定为正确的答案。
- 已有的四类对照结构（例如 `cached_destination_false` / `cached_destination_scoped` 这种"同一份证据、结论对与错成对"的设计）非常好用，**继续成对设计**。

**改动点**
1. 把用例表从 `review_optimization.ts` 抽到 `scripts/eval/review_benchmark_cases.ts`，字段保持 `{ id, question, source, answer, expected }`，另外**新增**：`category`（成对设计里的类别）、`origin`（`fictional` | `real-failure:<run_id>` | `real-correct:<run_id>`）。
2. 从历史失败里补入真实错误答案：**必须脱敏**——把客户姓名/电话/证件/单号/金额换成等长的占位值（保持形态，因为形态本身会影响复核判断）。新增 `scripts/eval/sanitize_case.ts` 做这件事，并在用例里记录原始 `run_id` 以便追溯。
3. 用例至少覆盖：适用范围过度泛化、纯资料请求被当成事实断言、引用与原文不符、声称已执行动作、条件分支只列一支、把"配置存在"当成"实际生效"。
4. 记录基线：在**改动复核之前**先跑一遍，把检出率（`expected=false` 被拦的比例）与误拦率（`expected=true` 被拦的比例）写进 `manifest.json` 之外的 `baseline.json`。

**步骤**
1. 抽取 + 脱敏 + 补用例。
2. 跑基线（**要花钱，先报预算**）：串行、每用例 2 轮。
3. 登记 `baseline.json`：总条数、分类分布、检出率、误拦率、P50/P90、token。
4. `npm test` 全绿（用例表是纯数据，但脚本要过类型检查）后提交。

**验收**：基准条数与类别分布登记在案；`expected` 的 SHA256 记录在 `manifest.json` 里；基线四项指标可复现；`review_optimization.ts` 原有用例**一条不少**。

**依赖**：S5（记账）、S7（先修掉 `performed_action` 误拦，否则基线里混着"永远过不了"的噪声）、S8（先修掉发布词表误杀，否则基准里混着词表噪声）。

**关口**：G3。

**风险与回滚**：真实失败答案经过脱敏后可能改变复核的判断（形态不变但语义可能被削弱）→ 脱敏后**必须人工过一遍**语义是否还成立。这份基准**只用于诊断**，不得用来宣称准确率。

## M3 复核思考档位实验（**必须在任何复核提示词改写之前**）

**目标**：搞清楚"复核用 high 太慢、用默认档是不是漏得更多"。这是目前最贵也最说不清的一个结。

**依据**
- 复核调用现在也带 `reasoning_effort=high`。
- 60 秒预算下高思考复核**全部超时**；默认档两阶段合计 30～68 秒完成，但同一批 5/5 通过里只有 2/5 内容可用。
- 180 秒预算下，能通过的复核要 128～172 秒。
- 所以"默认档更快"和"默认档漏检更多"目前**分不开**，必须用固定基准做对照。

**改动点**
- `server/src/config.ts`：新增 `reviewReasoningEffort`（环境变量 `REVIEW_REASONING_EFFORT`，取值 `default | low | high`，**默认保持现状**）。
- `server/src/agent/model.ts`：复核路径用 `reviewReasoningEffort`，调查路径继续用 `geminiReasoningEffort`。
- **只改这一个因素。** 提示词、超时预算、判断标准一律不动（S7 已经先做完，且 S7 不改判断）。

**步骤**
1. 用 M2 基准，三组（`default` / `low` / `high`），每组 2 轮，**串行**（并发会污染时延数据，之前的 120 次批次就吃过这个亏）。
2. 四类指标分开报：检出率、误拦率、P50/P90 耗时、token（输入/输出/思考/缓存）。
3. 结论只能写成相对比较，例如："在基准上，默认档的检出率 a%、误拦率 b%、P90 耗时 c 秒；high 档分别是 d%、e%、f 秒。选定 X 档，理由是……"
4. 把选定的档位写进 `server/.env` 示例与 `STATUS.md`；**在生产上生效要重启（G9）**。

**验收**：三组结果齐全；选定档位有明确理由；`manifest.json` 记录了模型名、`reasoning_effort`、超时、源码哈希。

**依赖**：M2、S7。

**关口**：G3（费用）。**必须先于任何复核提示词改写。**

**风险与回滚**：基准是虚构用例，**结论不能外推到真实工单**，只能作相对比较。若三组差别在噪声范围内（差值小于基准条数带来的不确定性），就按成本选，并明确写"未观测到可靠差别"。

## M4 盲评与评分工具

**目标**：Phase 5 要请开发盲评，先把这个流程做成可重复的工具，避免临场发明。

**依据**：现有评分是 Codex 单模型、评分时知道答案来自哪个配置、细则在生成之后才写 → 只能是银标签。开发盲评才是金标准。

**改动点**（新增，放在 `scripts/eval/` 下，产物落 `tests/eval/reports/`）
1. `make_blind_pack.ts`：输入同一工单的多个候选作答，输出**一页一工单**的盲评包。
   - 必须做：打乱候选顺序（用固定随机种子并记录）、隐去配置名/模型名/生成时间/耗时、每条候选只保留"结论 + 业务数据 + 证据摘要 + 客服话术 + 待核实项"。
   - 必须做：同一条工单的多个候选**用不同的随机字母标记**（A/B/C），且**标记到"哪个候选"的映射单独存一个文件**（盲评时不给开发看）。
2. `grade_sheet.ts`：生成打分表，每行四栏：参考答案要点 / 禁止断言 / 核心诉求 / 适用范围；每栏三选一：`符合 / 否决 / 修改`。追加一列自由文本。
3. `agreement.ts`：算评分者间一致率，用 S5 的区间函数给出不确定度；支持"同一评分者对同一工单的重复评分"（留出集随机抽 20% 复评）。
4. `workbook.ts`：从运行记录 + 打分表算出 README §5 的全部指标（覆盖率、交付正确率、严重误导率与单侧上界、违例率、时间 P50/P90、加时次数分布），并**分开统计银标签与金标准**。

**步骤**
1. 先用手上已有的运行记录造一份样例盲评包（不含真实 PII，或放在 git 忽略目录里）。
2. 自己按说明走一遍流程，把流程里卡住的地方写进 `docs/exec-plan-v3/90-appendix.md` 的对应模板。
3. `npm test` 全绿（新增脚本要过类型检查）后提交。

**验收**：样例包的一页里搜不到配置名、模型名、时间戳、候选原始顺序；标记到候选的映射存在且不在盲评页里；`workbook.ts` 能对已有的 120 次记录算出指标，且与 `00-README.md` §3 第 21 条的锚点一致（例如"150 单允许 8 个错误"）。

**依赖**：S5。

**关口**：无（工具本身不调模型；**用到真实数据时**才涉及 PII 规则）。

**风险与回滚**：盲评包里会出现客户数据，**只能放在被 git 忽略的 `tests/eval/reports/**`**，汇报里只用匿名编号和数量。用完按规定清理。
