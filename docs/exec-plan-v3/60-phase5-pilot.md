# Phase 5 · 真实工单摸底

前置：P1（工单集）依赖 G7；摸底 A 只需要 P1 + 一个隔离构建；摸底 B 依赖 Phase 1/3/4 完成。

## 先读这一段：摸底**不是**上线验收

| 工单总数 | 全部交付且全对时的单侧 95% 下界 | 0 例严重误导时的单侧 95% 上界 |
|---|---|---|
| 30 | 90.50% | 9.50% |
| 35 | 91.80% | 8.20% |
| 40 | 92.78% | 7.22% |

**30～40 单在统计上证明不了"正确率 ≥ 90%"**，更证明不了"严重误导为 0"（0/40 的上界还有 7.22%）。摸底的作用只有三个：

1. 校准**覆盖率**：真实工单里有多少是现有数据/工具能回答的。初始下限设 70%（D5），摸底后重定。
2. 看清**题型分布与失败构成**：规则题 / 历史事件题 / 具体订单排障各占多少；失败落在 M1 的哪几类。
3. 量出**真实耗时与加时次数**：15 分钟内完成多少、需要追加 5 分钟多少、P50/P90 是多少。

**任何摸底报告都不得写成"已达到上线正确率"。** 上线门槛只在正式验收的留出集上计算，规模由摸底结果反推。

**正式验收所需样本量（已算好，直接用）**
| 交付数 n | 允许错误数 | 下界 |
|---|---|---|
| 60 | ≤1 | 92.34% |
| 105 | ≤5 | 90.25% |
| 150 | ≤8 | 90.58% |

参考：真实正确率 95% 时，n=105 一次通过的概率只有 57%；97% 时才到 90%。**门槛实际要求约 96～97% 的真实正确率、75% 以上的覆盖率。** 反推工具是 S5 的 `scripts/eval/sample_size.ts`。

## 成本必须先算清楚 **[关口 G3 + G4]**

**实测锚点**：180 秒预算的一次完整流程，输入约 **5.9M token**（其中约 2.9M 命中缓存）。这是**每题每次**的量级。

| 方案 | 运行次数 | 输入 token 量级 |
|---|---|---|
| 30 单 × 1 轮 × 1 个阶段（A 或 B） | 30 | ≈ 180M |
| 30 单 × 1 轮 × 两个阶段（A + B） | 60 | ≈ 360M |
| 35 单 × 2 轮 × 两个阶段 | 140 | ≈ 840M |

对照：`00-README.md` §4 写的"累计超过 10M token 先停下问人"是**单任务**尺度。**摸底本身是 36～84 倍于这个尺度的一件事**，必须作为一个独立的预算项由用户明确批准（G3），并同时批准是否访问生产库与日志（G4）。

**推荐做法**
- 摸底 A 与 B **各只跑 1 轮**（不要 3 轮）。轮次用于看稳定性，那是正式验收的事。
- 先用 **3～5 单做冒烟**，确认整套运行、打分、记账链路能跑通，再花全量。
- 日常迭代用便宜的层：20 题的**固定证据**模式（`scripts/eval/model_ceiling.ts` 的 `evidence` 模式，单次调用、无工具轮次）远比完整流程便宜，用它做回归。
- 每一轮都要有台账（S5），阶段性报告里给出"实际用量 vs 预算"。

## P1 工单集构建 **[关口 G7]**

**目标**：把客服的原始工单变成一份可度量、可复现的问题集。

**依据**：D7（题来自客服工单与聊天记录，再加本机历史里约 40 个业务问题）；现有 20 题**全部是"按现行规则说明……"的规则题**，而本机真实提问里约三分之一是**具体订单排障**，两者不能互相代表。

**来源与规模**
- 客服负责人导出 **≥60 条**近期真实工单（含问题原文、附件、客服当时的处理结果），我们筛到 **30～40 条**；导出格式见 `90-appendix.md` 模板 B2。
- 本机历史里约 40 个业务问题（`tests/eval/reports/model-ceiling-20261009/historical-questions.json` 是既有的一部分）。
- 现有 20 题**不进**摸底集，它们继续当**开发集**用于诊断（用开发集结果宣称准确率是禁止的）。

**筛选与分层**（每一层都要有，不能全落在一类）
| 维度 | 取值 |
|---|---|
| 业务线 | 机票 / 酒店 / 火车票 / 打车 / 发票 / 短信通知 / 支付 / 其他 |
| 题型 | 现行规则 / 历史事件 / 具体订单排障 |
| 现有数据能否回答 | 能 / 不能（**答不了的题，正确输出就是诚实降级**，这是覆盖率的分母） |

**每条必须标注的字段**
`ticket_id`、业务线、题型、`core_demand`（**核心诉求**，一句话，由客服或开发给）、事件发生时间、数据快照时间、涉及的服务与代码版本、`answerable`（能/不能）、背景补充、附件清单、去敏状态。

**去敏规则（红线）**
- 客户姓名/电话/证件/订单/金额**保持原样**，因为这些正是要核对的数据；
- **不得**把工单内容写进 git 跟踪的文件、`STATUS.md` 或对话；
- 全部落在被忽略目录 `tests/eval/data/tickets/`，报告里只用匿名编号与数量。

**步骤**
1. 发出 G7 请求（T0.5 已发）；拿到后按上表筛选分层，**目标 30～40 条**。
2. 每条写出 `core_demand` 草稿，交客服负责人确认或改写（一句话，别让他们写长文）。
3. 对每题跑一遍"能不能答"的人工判断，只根据现有工具/数据能力，不看模型的回答。
4. 冻结：把题集用固定种子打乱并哈希，**冻结之后不许再增删**（增删要重新冻结并在 `STATUS.md` 记录）。
5. `npm test` 全绿后提交（**只有代码与文档进 git，工单数据不进**）。

**验收**：题集落盘且已冻结哈希；每条字段齐全；三层分布都有；`core_demand` 经客服确认；`answerable` 已判定。

**依赖**：G7（客服负责人导出）。

**关口**：**G7**。

**风险与回滚**：客服导出的工单可能集中在少数几个话题上（真实客服台常有这种偏斜）→ 分层时如实记录，**不要为了凑分层去造题**。偏斜本身就是要报告的结果。

## P2 摸底 A（改进前基线）

**目标**：在**基线提交**上跑一遍，拿到"改进前"的真实数字。

**依据**：摸底 A 必须在**冻结的基线构建**上跑，不能在生产 `dist` 上跑——已核实 `server/dist/agent/model.js` 与源码不一致，用它会得到一个既不是基线也不是候选的中间态。

**做法**
1. 用 `636adda` 建一个隔离构建（`npm run build`），起隔离服务端（端口 8691–8699 之一，`CODE_SYNC_ENABLED=false`，见 `tests/helpers/isolated_server.ts`）。
2. 按 P1 的题集跑 **1 轮**，逐题记录：结局（`delivered` / `unresolved_honest` / `wrong` / `severe`）、是否命中 `core_demand`、耗时、加时次数、token、`version_drift`、因版本未知而降级的次数。
3. 每题的**工具结果原文**要存档——M1 归因与以后的事故复盘都要用。
4. 记账写进台账；报告落 `tests/eval/reports/exec-v3/pilot-A.md`（git 忽略）。

**验收**：题集 100% 有记录；结局分布、覆盖率、耗时 P50/P90、token、失败构成齐全；没有题因为脚本问题被静默跳过（跳过的要写明原因与数量）。

**依赖**：P1、S5。

**关口**：**G3 + G4**（预算与"是否访问生产库与日志"要用户批准）。

**风险与回滚**：业务库是**实时库，没有事务快照**——同一题在不同时间跑会看到不同的数据。所以每题要记录"数据快照时间"，且 A 与 B 必须**尽量在同一时间窗内**跑；做不到就在报告里写明时间差。

## P3 摸底 B（改进后）

**目标**：用同一套题、同一套配置、在 Phase 1/3/4 的候选构建上再跑一遍，与 A 对照。

**做法**：与 P2 完全相同的流程，只换构建。**唯一允许的差异是代码本身**：模型名、`reasoning_effort`、超时、预算、并发、题集顺序全部保持一致，并把这些写进两份报告的"配置快照"里。

**验收**：A 与 B 的配置快照逐项可比（不同的项要显式列出并说明理由）；逐题结局可与 A 配对对照；新增了"因版本未知降级"一栏。

**依赖**：Phase 1/3/4、P1、S5。

**关口**：**G3 + G4**。

**风险与回滚**：A 与 B 之间如果还有别的变更（比如模型中转改了路由），结论就不成立 → 每次运行都要记录源码哈希与配置快照（`00-README.md` §4 已有要求），发现不可比的项就**停止对照**并说明。

## P4 盲评与门槛重新推导 **[关口 G8]**

**目标**：把银标签换成金标准，并用摸底结果重新推导正式验收的门槛。

**依据**：现有全部评分都出自 Codex 一个模型，评分时知道答案来自哪个配置，细则在生成之后才写 → 只能是银标签。D6 定的是开发同事核对参考答案，G8 定的是开发盲评摸底输出。

**做法**
1. 用 M4 的工具生成盲评包：打乱候选顺序、隐去配置名/模型名/时间，一页一工单。**每条约 5 分钟**，30～40 条合计约 3 小时开发时间——**要提前排期**，这是全流程最紧的人力瓶颈。
2. 打分表四栏（参考答案要点 / 禁止断言 / 核心诉求 / 适用范围）逐条 `符合 / 否决 / 修改`。
3. 抽 20% 做重复评分，算评分者间一致率（用 S5 的区间函数给不确定度）。
4. 只对**分歧条目、全部严重误导、以及随机 20% 样本**做裁定。
5. 用盲评结果重算：覆盖率、交付正确率（含话术）、严重误导率与上界、违规率、耗时分布。**银标签与金标准分开统计。**
6. 重新推导正式验收门槛：
   - 覆盖率下限：从摸底的实际覆盖率反推（初始 70% 可能过高或过低）；
   - 所需样本量：用 `scripts/eval/sample_size.ts`，输入"期望下界 90%"与"摸底观测到的正确率"，算出需要的交付数 n，再按预期覆盖率换算成工单总数；
   - 明确写出"要多少次运行、大约多少 token、需要多长时间"。
7. 报告落 `tests/eval/reports/exec-v3/pilot-BLIND.md`（git 忽略）。

**验收**：盲评覆盖全部摸底题；一致率有数字；门槛推导过程可复算（脚本 + 输入都留档）；报告里明确写出**"摸底给不出上线结论"**。

**依赖**：P2、P3、M4。

**关口**：**G8**。

**风险与回滚**：开发核对与盲评是**外部依赖，会拖进度**。所以 P1 一冻结就把盲评排期发出去，不要等跑完才约。

## 后续（本轮只写启动条件，不执行）

以下五件事**都不在本轮范围内**。等到条件满足时再单独规划。

### 1. 正式验收（150 单级）
**启动条件（全部满足）**：
- 摸底 B 的盲评结果显示交付正确率点估计 **≥93%**、覆盖率 **≥75%**（留出余量，因为门槛实际要求 96～97% 与 75% 以上）；
- P4 已用 `sample_size.ts` 反推出所需工单数与运行次数，并写明成本；
- 留出集已独立冻结（**不参与任何调优**，P1 的集子可作为留出集的一部分，但不能再被改）；
- **`scripts/eval/release_gate.mjs` 已按新口径重写**：它现在硬编码"20 题 × 3 轮 × 2 版本 = 120 次评分"、候选要 ≥54/60 可用与 ≥59/60 正常结束、8 项验证全真。**换成工单集之后这套判据全部失效**，必须先改门禁再谈验收。

### 2. 模型对照（K3 / GLM / DeepSeek）
**启动条件**：M2 基准稳定；隔离实例能跑通完整流程；用户批准预算；**串行执行**（并发会污染时延数据，之前吃过这个亏）。D8 已定：这些模型只作对照，不切换生产。

### 3. 规则卡内容撰写
**启动条件**：M1 归因显示"适用范围说大"是首要失败类别；且开发愿意核对内容（D6）。规则卡是**开发签字的内容**，不是模型生成的。

### 4. 不可变源码快照
**启动条件**：V3 已把 `snapshot-manifest.json` 并进图谱重建流程（现在它和实际图谱不同步）；且已决定要发布。

### 5. `npm run build:exe` 与发布分发
**启动条件**：留出集验收通过；`release_gate.mjs` 已重写并通过；隐私、迁移、Chrome、EXE 各项验证齐全；**候选包必须复制已通过验收且哈希匹配的那一份，不得在发布阶段重建**。
**红线**：任何情况下都不要在没有这些条件时运行 `build:exe` 或写 `server/data/releases/`。
